Valve Shutdown Reporting — Edge Platform

Pluto LNG plant ke safety shutdown valves kitni tezi se apni safe position tak pahunchte hain — ye measure karne wala edge system. Chaar AWS IoT Greengrass components, plant ke andar chalte hain, aur result cloud par bhejte hain. Ye page repo + DR document dono ka ek jagah summary hai.

00TL;DR — 60 second version

Plant mein shutdown valves lage hain. Emergency mein inhe apni safe position (open ya close) par pahunchna hota hai. Kitne seconds lage — usko stroke time kehte hain. Agar valve slow ho raha hai, matlab wo ghis raha hai — maintenance chahiye. Ye system wahi stroke time automatically measure karta hai.

Ek line mein

PHD historian se valve events padho → filter karo → state machine chalao → stroke time nikaalo → PASS/FAIL grade karo → SiteWise par publish karo. Sab kuch plant ke andar, edge par.

Is line ka har step kis component ke andar chalta hai — section 06 mein step-by-step breakdown hai.

Aapka ticket kya hai

Har component apni state file disk par likhta hai — sabse important hai cursor, yaani "PHD mein kahan tak padh liya". Ye file kahin backup nahi hoti. Agar edge device ka disk gaya, cursor gaya — aur collector now − 2 minutes se dobara shuru karta hai.

⚠ Core problem

Device loss = permanent data gap jitni der outage chala. Duplicate nahi — gap. Aur ye sirf ek WARNING log chhodta hai, koi alarm nahi. Yahi DR document ka R1 risk hai aur yahi fix karna hai.

Do contracts jo sab kuch jodte hain

Jab dono sire black box hain, to system tabhi chalta hai jab contract clear ho. Yahan sirf do hain:

Input contract — PHD ki taraf

Hamara code PHD se “baat” nahi karta. Bas ek read-only SELECT maarta hai aur 5 columns expect karta hai:

UF_EVENT_DATA_ID   # dedup key
ACTUAL_TIME        # event kab hua
REC_UPD_DATE       # cursor isi par
EVENT_NAME         # kaunsa tag
VALUE1             # TRIP/NORMAL, TRUE/FALSE

Output contract — SiteWise ki taraf

Yahan asli trick hai: hamara code SiteWise ka koi API call nahi karta. MQTT topic ka naam hi property alias hai:

self.mqtt.publish(property_alias, json.dumps(payload))
#                 ↑ topic = "/34UV202/RESULT"

Payload SiteWise ka standard PutAssetPropertyValueEntry format hota hai. Edge Publisher usi broker ko sun raha hai, alias se asset property dhoondta hai, aur cloud par bhej deta hai.

Isiliye calculator mein boto3 hai hi nahi

Poora publish path sirf MQTT hai. Ekmatra component jo AWS SDK use karta hai wo sync-metadata hai — kyunki usay SiteWise se padhna hota hai. Isiliye backup component ke liye wahi template hai.

Dev mein PHD hota hi nahi

Collector recipe ka default DB_URL ek AWS RDS SQL Server hai (windfall-np-platform-mssql…rds.amazonaws.com), asli plant PHD nahi. Dev/QA mein PHD ka stand-in chalta hai. Local testing ke liye vagrant/ folder poora Greengrass core + SiteWise Edge gateway khada karta hai.

Part B — Cloud path (result ke baad)

Kyun edge par?
  • Network: Plant ka link slow/intermittent hai. Har event cloud bhejna practical nahi.
  • Reachability: PHD SQL Server plant ke andar hai, cloud se reach hi nahi hota.
  • OT security: Plant ka raw data seedha internet par nahi ja sakta.
  • Volume: Hazaaron raw events se sirf kuch results banate hain — filtering edge par sasti hai.

03Greengrass 101 — sirf utna jitna chahiye

AWS IoT Greengrass = edge runtime. Aap apna code device par chalate ho, lekin manage cloud se karte ho — kaun sa component, kaun se version, kis device par.

Sabse pehle — Greengrass koi device nahi hai

Ye sabse aam confusion hai. AWS koi hardware nahi bhejta. Greengrass sirf software hai — ek Java program jo aap apni machine par install karte ho. Console mein jo “Core device” dikhta hai wo sirf ek registration entry hai, AWS ki machine nahi.

Sabse aasan mental model: socho jaise koi monitoring agent apne server par install karte ho. Dashboard cloud mein hai, control cloud se hota hai — par server aapka hi hai.

Install kaise hota hai — manual staging

Plant ki machine par general internet nahi hai. Isliye Greengrass ka JAR download nahi hota — koi insaan use pehle machine par rakh ke aata hai. Ye poora process manual hai, aur DR ke liye ye jaanna zaroori hai.

Pehle ek farq samajh lo
General internet — CloudFront, PyPI, GitHub BAND
AWS endpoints — IoT Core, S3 — proxy ke through KHULA

Agar S3 reachable na hota to Greengrass hamare components deploy hi nahi kar pata. Toh machine AWS se judi hui hai — bas ek controlled proxy ke through. “No internet” ≠ “no AWS”.

Poora install flow

  1. Zip download karo — kisi aur machine par

    Internet-wali machine par AWS ke public CDN se:

    https://d2s8p88vqu9w66.cloudfront.net/releases/greengrass-nucleus-latest.zip
  2. Plant machine par stage karo

    OT ke approved transfer path se file ko C:\Temp\ mein daalo. Installer ka default $SourcePath yahi hai.

  3. PowerShell installer chalao

    Machine par, Administrator ke roop mein:

    core-device-installer.ps1 -ConfigPath "C:\windfall_installers\wfp-prd-plp-shared-01.json"
  4. Script baaki sab karta hai

    C:\Temp se zip uthata hai → unzip → Java install → certificate laata hai → java -jar Greengrass.jar chala kar C:\greengrass\v2 mein install karta hai → Windows service bana deta hai.

Code khud ye batata hai

Function ka naam DownloadFile() hai — par andar dekho, kuch download hota hi nahi: 

hidden [void] DownloadFile([ArtifactUri] $ArtifactUri, [string] $OutFile) {
    # Nucleus is staged locally (offline/OT). Resolved to a full path in Paths.SetPaths.
    Write-Info "Copying locally staged nucleus zip: $($this.Paths.NucleusZipPath)..."
    Copy-Item $this.Paths.NucleusZipPath -Destination $OutFile -ErrorAction Stop
}

Naam purana reh gaya — script pehle internet-connected machines ke liye likha gaya tha, phir OT ke liye offline bana diya gaya. Java aur Root CA ke saath bhi wahi hua:

#! Java is installed directly from the locally-staged Corretto MSI in the source
#! folder (see InstallJava). No download/copy needed — there is no internet in OT.

Ticket ka connection — RTO yahin jaata hai

Device rebuild karne ka matlab hai ye poora manual process dobara:

Nucleus — device ka “operating system”

Jab installer chalta hai, jo install hota hai wahi Nucleus hai. Baaki sab — aapke chaar components, StreamManager, EMQX — uske neeche chalte hain. Ek line mein: Nucleus device par systemd + package manager + message bus teeno ka kaam ek saath karta hai.

#KaamKya karta hai
1 Deployments IoT Core se connected rehta hai. Order aane par S3 se artifact zip download karta hai, unzip karta hai, recipe padhta hai, components start karta hai. Isiliye code S3 par safe hai — device wipe karke naya Greengrass install karo, sab dobara aa jayega.
2 Component lifecycle Recipe ka Install phir Run script chalata hai. Aur agar process non-zero exit kare to restart kar deta hai.
3 Configuration inject karna DefaultConfiguration + deployment overrides merge karta hai, aur Setenv block ke through environment variables bana deta hai. Isiliye config badalne ke liye redeploy zaroori nahi — debug console se live badal sakte ho.
4 IPC broker /cej/component/control aur cloudwatch/metric/put wala local pub/sub Nucleus deta hai — aur permissions bhi wahi enforce karta hai (recipe ka accessControl). Ye EMQX se alag hai (section 04).
5 Dependencies resolve karna Recipe mein sirf aws.greengrass.StreamManager: ^2.0.0 likha hai. Nucleus usko AWS catalog se khud download+install karta hai, aur pehle usko start karta hai, phir aapka component.
6 Credentials + logs TES (Token Exchange Service) components ko temporary AWS credentials deta hai bina keys hardcode kiye — sync-metadata ka boto3 isi se chalta hai. Aur har component ka stdout/stderr capture karke file mein daalta hai.

Point 2 code mein — deliberate crash

Collector jaan-boojh kar crash karta hai taaki Nucleus use restart kar de:

if worker_failed.is_set():
    # Non-zero exit so Greengrass treats this as a failure and restarts.
    sys.exit(1)

Ye ek zinda process chhodne se behtar hai jiska worker thread mar chuka ho aur jo kuch collect hi na kar raha ho. Calculator bhi stream_listener() fail hone par yahi karta hai.

Nucleus supervisor hai, orchestrator nahi

Aam galatfehmi: log samajhte hain Nucleus poore pipeline ko coordinate karta hai. Nahi karta. Chaaron recipes ki ComponentDependencies dekho: 

collector      →  aws.greengrass.SecretManager
data-filter    →  aws.greengrass.StreamManager
vsr-calculator →  aws.greengrass.StreamManager
sync-metadata  →  aws.greengrass.TokenExchangeService

Koi bhi component doosre hamare component par depend nahi karta — sirf AWS wale declare kiye gaye hain. Nucleus ke liye ye chaar bilkul unrelated processes hain, aur wo inhe kisi bhi order mein start kar sakta hai.

Isiliye handshake application-level hai

Startup order hamara Python khud sambhalta hai — metadata ka wait, PING/PONG, START (section 06). Nucleus us IPC message ko sirf deliver karta hai; usay pata nahi START ka matlab kya hai. Aur dependencies declare karne se bhi kaam nahi banta: Nucleus ke liye “process zinda hai” kaafi hai, wo ye nahi jaan sakta ki filter ne MQTT topic par subscribe kar liya ya nahi.

Isi tarah Nucleus data path mein hai hi nahi. Usne bas ye Python processes spawn kiye the; uske baad data usko chhoota tak nahi:

04MQTT Broker — EMQX

Fig 1 mein collector aur data-filter ke beech jo MQTT 1883 label hai — wo koi library call nahi hai. Device par ek alag process chal raha hai jo messages route karta hai. Uska naam EMQX hai, aur poore edge pipeline ka do-tihaai traffic usi se guzarta hai. Ye section batata hai wo cheez hai kya, define kahan hai, aur ticket ke liye kyun matter karti hai.

EMQX hai kya

EMQX ek open-source MQTT broker hai (Erlang/OTP mein likha gaya). Kaam simple hai — ek message post office: koi client ek topic par message publish karta hai, doosre clients us topic ko subscribe karte hain, aur broker beech mein deliver kar deta hai. Publisher aur subscriber ek doosre ko jaante hi nahi — bas topic ka naam share karte hain.

Hamare case mein AWS ne EMQX ko ek Greengrass managed component ke roop mein package kiya hai — aws.greengrass.clientdevices.mqtt.EMQX. Matlab hum broker install nahi karte, uska code maintain nahi karte; deployment mein bas uska naam + version + config likhte hain, aur Nucleus usko Docker container ki tarah utha deta hai.

Kya karta hai

Topic-based pub/sub routing. In-memory. Local, plant ke andar — internet ki koi zaroorat nahi.

Kya nahi karta

Messages store nahi karta. Subscriber offline hai to message gir jaata hai. Ye database nahi hai.

Kyun zaroori

Components alag OS processes hain. Unke beech baat karne ka ek common, language-neutral raasta chahiye.

Define kahan hai — is repo mein nahi

Ye important hai: broker ka koi zikr windfall-greengrass-components mein nahi milega. Wo doosre repo, windfall-platform-automation, ki SiteWise-gateway CloudFormation templates mein define hai — har core device ke liye ek template:

Broker do alag kaam karta hai

Aam taur par log sochte hain broker sirf collector → filter wala hop hai. Actually output path bhi usi broker se jaata hai — aur wo hissa zyada interesting hai.

1 · Internal event bus

collector har 60 second PHD se rows nikaal kar cej/event/data par daalta hai; data-filter wahi sun raha hota hai.

Yahan broker sirf ek pipe hai — do processes ke beech.

2 · Output path = SiteWise ka “API”

vsr-calculator SiteWise ka koi API call nahi karta. Wo bas MQTT par publish karta hai, jahan topic ka naam hi property alias hai:

self.mqtt.publish(property_alias, payload)
# topic = "/34UV202/RESULT"

SiteWise Edge Publisher usi broker ko sun raha hai, alias se asset property dhoondta hai, aur cloud par sync kar deta hai.

Dono raaste ek hi process se guzarte hain

Ek hi EMQX instance internal bus aur SiteWise output dono handle karta hai. Matlab broker gir gaya to sirf ingestion nahi rukti — results publish hona bhi ruk jaata hai. Alias-based publish ka detail output contract mein hai.

Bridge ≠ broker

aws.greengrass.clientdevices.mqtt.Bridge alag component hai. Wo broker nahi hai — wo sirf local → cloud forwarder hai. Gateway CFN mein uska mapping sirf ek topic ke liye hai: cej/event/data-replica (Pubsub → IotCore) — ye CEJ data-replica workstream ke liye hai, VSR ke liye nahi. Ticket ke liye kya matter karta hai

1 · Zero persistence — isiliye startup handshake hai

Broker messages store nahi karta. Agar collector publish karna shuru kar de aur data-filter abhi subscribe hi na hua ho, wo events hamesha ke liye gayab — aur cursor aage badh chuka hoga, to PHD se dobara bhi nahi milenge. Yahi wajah hai ki collector khud se start nahi hota; filter pehle ready hota hai, phir IPC par START bhejta hai. Fig 5 dekho.

2 · Broker down ho jaaye to data loss nahi hota

Collector ka two-phase commit yahan bachata hai: publish fail = cursor commit nahi hota, aur agli poll par wahi batch dobara padha jaata hai. Matlab broker outage throughput rokta hai, data nahi. Ye scenario B/D jaisa hi behaviour hai.

3 · Docker ek chhupi hui dependency hai

EMQX Docker container mein chalta hai. Agar device par Docker install/running nahi hai, gateway deployment successful dikhega par broker runtime par fail hoga — aur poora pipeline chup-chaap ruk jaayega. Isliye install_scripts/core-device-installer.ps1 mein ek explicit pre-flight ValidateDocker() warning hai. Host rebuild karte waqt (DR scenario A) ye step runbook mein hona chahiye.

4 · Backup scope mein nahi hai

Broker hamari state nahi rakhta — in-flight messages sirf RAM mein hote hain, aur uska apna data emqx-data Docker volume mein alag rehta hai (users/ACL). Us volume mein hamara koi business data nahi hai, aur components 1883 par bina auth connect karte hain — to volume ka backup lena zaroori nahi. Backup component ka scope sirf chaar components ki work-directory state files hai.

Kafka kyun nahi?

Wajib sawaal — aur jawab hai ye edge hai, cloud nahi. EMQX ek Docker container hai; Kafka ke liye JVM broker + HA ke liye multiple nodes chahiye, jo ek plant gateway par practical nahi. Aur MQTT hi wo protocol hai jo SiteWise, IoT Core aur field devices sab natively bolte hain. Jahan durable, replayable log chahiye — wahan is design mein pehle se StreamManager (edge) aur Kinesis/SQS (cloud) use ho rahe hain. Isliye broker ko Kafka banne ki zaroorat hi nahi hai.

07Valve Domain Logic

Stroke kya hai?

Ek stroke = valve ka poora movement, trip command se lekar physical confirmation tak. Safety valve ko emergency mein apni safe position par pahunchna hota hai — kitna time laga, wahi measure karte hain.

Chaar valve types

Naam do cheezein batata hai: safe direction (OPEN/CLOSE) aur kitne signals monitor hote hain (2M/3M).

TypeSafe positionMonitored signalsStroke kab complete
OPEN_2MOpen (depressurize)TRIGGER + SRSR aate hi
OPEN_3MOpen (depressurize)TRIGGER + SR + LIFTSR aur LIFT dono — jo baad mein aaye
CLOSE_2MClose (isolate)TRIGGER + SRSR aate hi
CLOSE_3MClose (isolate)TRIGGER + SR + LIFTSR aur LIFT dono
"M" ka matlab

Repo mein spell out nahi hai, lekin code se saaf hai: M = monitored signal count. 3M valves mein ek extra limit switch (LIFT) hai, isliye unka stroke end max(SR_timestamp, LIFT_timestamp) hota hai — kyunki dono kisi bhi order mein aa sakte hain.

Teen signals

TRIGGER

Operator/DCS ka command. Values normalize hote hain TRIP ya NORMAL mein.

stroke START

SR

Close-side limit switch. TRUE/FALSE. CSV warnings isse "close switch" kehti hain.

confirmation

LIFT

Open-side limit switch. Sirf 3M valves mein. CSV warnings isse "open switch" kehti hain.

3M only

Hand Switch (HS) ka special case

Kuch valves operator ke physical hand switch se trip hote hain. Problem: HS ek momentary pulse hai — 2–3 second baad TRIGGER wapas NORMAL ho jaata hai, jabki SR/LIFT abhi aaye hi nahi.

Naive state machine isse "operator ne cancel kar diya" samajh kar stroke fail kar deta. Isliye hs_lifecycle.py alag rules lagata hai:

  • Suppression — mid-stroke NORMAL ko ignore karo, DCS ne trip latch kar rakha hai.
  • Coalescing — trip already latched ho to doosra TRIP same stroke maano.
  • Rearm — complete hone ke baad valve ko wapas armed state par le jao, taaki physical reopen "rebound" na samjha jaye.
  • Expiry — 5 minute tak SR/LIFT na aaye to trip fail kar do.

09Grading & Outputs

Stroke complete hone par time nikalta hai, phir usko valve ke apne thresholds (MATT, MERT, MART) se compare karke grade diya jaata hai.

Grading logic (verbatim)

def calculate_result(stroke_time, matt, mert, mart):
    if   stroke_time <= 0                  : return "INVALID"
    elif stroke_time < matt               : return "FAIL FAST"
    elif matt <= stroke_time <= mert     : return "PASS"
    elif mert < stroke_time <= mart      : return "PASS SLOW"
    else                                  : return "FAIL"

Backup component — design notes

Permissions

Chaaron components default user par chalte hain (koi RunWith override nahi; calculator recipe chown ggc_user:ggc_group karti hai). To ek sibling component unki work dirs padh sakta hai.

verify on device Commit karne se pehle confirm kar lena.

Snapshot order (critical)

Calculator ke liye pehle cursor, phir checkpoint padho.

Ulta order restored cursor ko checkpoint se aage le ja sakta hai — aur beech ke in-flight strokes chup-chaap gayab.

Cross-component consistency

Zaroorat nahi hai. Har component ka apna write atomic hai aur replay safe design hai.

Global quiesce mat banao — over-engineering hai.

Monitoring

Existing pattern reuse karo: IPC → cloudwatch/metric/put (dekho services/metrics.py).

Naya mechanism mat banao. Alarm: "2× cadence tak koi successful backup nahi".

Sasta complementary fix

Har recipe mein ek STATE_DIR config add karo, taaki state path CWD par depend na kare. Chhota, low-risk change — aur backup component ko path guess nahi karna padega.

Ek baat yaad rakhna

Stale cursor restore karne se duplicates aayenge (5 min tak) — aur wo theek hai. Missing cursor se gap aata hai — aur wo theek nahi hai. Duplicates recoverable hain, gaps nahi. Design hamesha duplicates ki taraf jhukna chahiye.
